# n8n automation

n8n coordinates the steps. The Next.js app and the database enforce every rule: eligibility, suppression, consent, approval of the exact draft version, and sending limits. n8n holds no database key and no email-provider key. It has only two signing secrets and, if sending is ever enabled, a Gmail credential that can only send.

```
site form ─▶ crm_intake (one transaction) ─▶ outbox_events
admin action (discovery import, "Request draft", "Send") ─▶ outbox_events
                                                   │
n8n "Ops · Outbox pump" (every minute) ─signed─▶ POST /api/automation/outbox.dispatch
                                                   │  claim (lease) → sign → POST to n8n webhook → delivered / retry / dead
                                                   ▼
n8n workflows A–D ─verify signature─▶ run.start (dedupe) ─▶ 202 ─▶ signed callbacks /api/automation/<action> ─▶ run.finish
n8n workflow E (schedule) ─▶ followups.prepare (drafts only)
any failure ─▶ "Gravityy · Errors" ─▶ run.fail (logs + emails the admin)
```

**Safe by default.** Nothing is sent and no paid API is called until you turn it on.
- Sending needs **both** `OUTREACH_SENDING_ENABLED=true` in Vercel **and** the *Send via Gmail* node enabled in n8n. Even then, an email goes out only after an admin presses **Send** on an approved draft.
- Reoon (paid) stays off until `REOON_API_KEY` is set in Vercel.
- AI drafting is not wired in. Drafts are fixed templates that an admin edits.

## Workflows (`n8n/workflows/`)

| File | Trigger | Steps |
|---|---|---|
| `A-inbound-leads.json` | `lead.created` (webhook `gravityy-inbound-lead`) | verify HMAC → dedupe → Reoon check (app, off by default) → rescore → CRM update → admin email → optional reply **draft** for MQLs |
| `B-outbound-research.json` | `discovery.completed` (`gravityy-outbound-research`) | job started by an admin from an approved source (CSV with lawful basis, or approved provider) → website analysis in batches of 5 (robots.txt respected) → scoring → companies stay in the review queue → admin email |
| `C-outreach-drafts.json` | `outreach.draft_requested` (`gravityy-outreach-draft`) | suppression + consent/enquiry + 7-day cool-down → template draft `pending_approval` → admin reviews/edits/approves in **Admin → Outreach** |
| `D-gmail-send.json` | `outreach.send_requested` (`gravityy-gmail-send`) | only after an admin presses Send: re-check switch, approved exact version, eligibility, daily limit → Gmail (disabled node) → record message id + status |
| `E-follow-up-drafts.json` | weekdays 09:30 | sends 7+ days old with no reply/bounce/unsubscribe → follow-up **drafts** (never sent automatically) |
| `ops-outbox-pump.json` | every minute | asks the app to deliver due outbox events |
| `errors.json` | Error Trigger | marks the run failed, emails the admin |

The JSON is generated by `scripts/build-n8n-workflows.mjs`, so edit that script and re-run it rather than editing the JSON by hand. `npx tsx scripts/check-automation.mts` checks:
- the JSON contains no secrets or credentials;
- the Gmail node is disabled;
- every Code node parses;
- both signing directions agree.

## Event contracts (v1)

Every delivery uses one envelope: `{ id, type, version: 1, occurred_at, workspace_id, data }`. It is strict (no unknown fields), and the `data` part holds IDs and counts only, never personal data. The schemas live in `lib/events/contracts.ts`.
- **Adding** a field keeps `version: 1`.
- **Renaming or removing** a field means a new version. Workflows reject versions they don't know (*Verify signature* node).

| type | data |
|---|---|
| `lead.created` | `lead_id, source (contact\|audit), score, qualification (unqualified\|mql), suppressed` |
| `discovery.completed` | `job_id, source, provider, status, found, imported, duplicates, rejected` |
| `outreach.draft_requested` | `contact_id, lead_id \| null, purpose (reply\|outreach)` |
| `outreach.send_requested` | `send_id, draft_id, draft_version` |
| `website.analyzed`, `lead.scored`, `crm.updated` | recorded only (no workflow consumes them yet) |

## Signing (both directions)

Header: `X-Gravityy-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256(secret, "<t>.<raw body>")>`. The receiver rejects a timestamp more than 5 minutes off.

| Direction | Secret (app name / n8n name) | Extra protection |
|---|---|---|
| app → n8n webhooks | `N8N_OUTBOUND_SECRET` / `GRAVITYY_WEBHOOK_SECRET` | event `id` deduplicated by `run.start` |
| n8n → app `/api/automation/<action>` | `N8N_CALLBACK_SECRET` / `GRAVITYY_CALLBACK_SECRET` | `X-Request-Id` (uuid) is single-use (`webhook_events`, kept 24 h) |

Generate each secret with `openssl rand -hex 32`. Use different values for app→n8n and n8n→app, and different values again for development and production.

## Environment variables

### Vercel (Next.js)

Set Production and Preview/Development separately.

| Variable | Default | Purpose |
|---|---|---|
| `N8N_WEBHOOK_BASE_URL` | empty (events wait in the outbox) | e.g. `https://n8n.example.com/webhook`; for dev, the dev n8n instance |
| `N8N_OUTBOUND_SECRET` | empty | signs app → n8n |
| `N8N_CALLBACK_SECRET` | empty (API returns 503) | verifies n8n → app |
| `OUTREACH_SENDING_ENABLED` | `false` | first sending switch |
| `OUTREACH_DAILY_LIMIT` | `20` | max sends per rolling 24 h (1–200) |
| `REOON_API_KEY` | empty | **paid**; email verification for inbound leads |

### n8n instance

Set these in the environment of each n8n instance, not in the workflows.

| Variable | Purpose |
|---|---|
| `GRAVITYY_APP_URL` | `https://www.gravityystudio.com` (prod) or your preview / `http://host.docker.internal:3000` (dev) |
| `GRAVITYY_WEBHOOK_SECRET` | = the app's `N8N_OUTBOUND_SECRET` |
| `GRAVITYY_CALLBACK_SECRET` | = the app's `N8N_CALLBACK_SECRET` |
| `GRAVITYY_REPLY_DRAFTS` | `false` disables Workflow A's optional reply drafts |
| `N8N_BLOCK_ENV_ACCESS_IN_NODE=false` | lets Code nodes read the `GRAVITYY_*` values |
| `NODE_FUNCTION_ALLOW_BUILTIN=crypto` | lets Code nodes compute HMACs |
| `GENERIC_TIMEZONE=Asia/Kolkata` | schedule for Workflow E |

Because Code nodes can read `$env`, anyone who can edit workflows on that instance can read these two secrets. Keep editor access to the owner, and rotate the secrets if that changes.

### Credentials (minimal scope)

- **Gmail (send only):** this is the only n8n credential. It is a Google OAuth2 client limited to the `https://www.googleapis.com/auth/gmail.send` scope. Attach it to *Send via Gmail* only when sending is approved.
- **No Supabase, Resend or Reoon keys in n8n.** Those stay in Vercel.

### Development vs production

Run two n8n instances (or two n8n projects), each with its own pair of secrets and its own `GRAVITYY_APP_URL`.
- Point Vercel **Preview** at the dev instance and **Production** at the prod instance.
- A dev event can't run a prod workflow: the signature would fail.
- Keep Gmail disabled in dev permanently.

## Setup

1. **Database.** `supabase/migrations/20261023060000_automation.sql` is already applied to the live project. Tests: `supabase/tests/automation.sql` (29 checks). Like the other SQL tests it rolls back, so run it anytime.
2. **Secrets.** Generate four secrets: outbound and callback, for both dev and prod.
3. **n8n environment.** Set the variables above and restart n8n.
4. **Import.** n8n → *Workflows → Import from file*. Import all seven files.
5. **Error workflow.** In each of A, B, C, D, E and Ops, open *Settings → Error workflow* and choose **Gravityy · Errors**.
6. **Activate.** Activate Errors, Ops pump, A, B, C and E. Activate D too; while Gmail is disabled, every send request is cancelled and recorded.
7. **Vercel.** Set `N8N_WEBHOOK_BASE_URL` (the production webhook URL, ending `/webhook`), `N8N_OUTBOUND_SECRET` and `N8N_CALLBACK_SECRET`, then redeploy.

## Verification

All of these use fictional data and send nothing to customers.

1. **Unit checks.**
   ```bash
   npx tsx scripts/check-automation.mts
   ```
2. **Callback auth.** Send without a signature and expect `401`. Then send a signed request and expect `200`; it emails the admin inbox, or logs to the console while Resend is unset:
   ```bash
   N8N_CALLBACK_SECRET=<dev secret> node scripts/n8n-send-test.mjs https://<app>/api/automation/notify.admin n8n/test-payloads/callback.notify.admin.json
   ```
3. **Webhook auth in n8n.** Open workflow A, click *Listen for test event*, then send:
   ```bash
   N8N_OUTBOUND_SECRET=<dev secret> node scripts/n8n-send-test.mjs https://<n8n>/webhook-test/gravityy-inbound-lead n8n/test-payloads/event.lead.created.json
   ```
   *Verify signature* should pass. The next step fails with "lead not found", which is expected: the test lead ID is fictional. Re-send with a wrong secret and *Verify signature* fails.
4. **End to end.**
   - Submit the contact form with a fictional business address, e.g. `test+n8n@example.com`.
   - Within a minute the pump delivers `lead.created`. Workflow A runs, the admin email arrives, and **Admin → Outreach → Workflow runs** shows `A-inbound-lead succeeded`.
   - Delete the test lead afterwards (Admin → Leads).
5. **Sending stays off.**
   - Approve a draft. Its Send button reads "Sending disabled".
   - With `OUTREACH_SENDING_ENABLED=true` but the Gmail node still disabled, pressing Send ends with status `failed` ("Gmail node disabled"). Nothing is sent.

## Failure recovery

| Symptom | Where you see it | What to do |
|---|---|---|
| n8n down, or a webhook returns 4xx/5xx | **Admin → Outreach → Dead letters & retries** (status `failed`, next attempt shown) | Nothing. Retries back off (2, 4, 8 … minutes, up to 6 h). |
| Event `dead` after 8 attempts | Same table, plus an admin email | Fix the cause (URL, secret, workflow inactive), then press **Requeue**. Deduplication makes a repeat harmless. |
| Workflow fails after accepting (202) | Error email; run `failed` in *Workflow runs* | Fix the cause, then n8n → *Executions* → **Retry**. Every step is safe to repeat. |
| Signature errors everywhere | `Bad signature` in n8n, or `401` from the app | The secrets differ, or clocks are more than 5 minutes apart. Re-paste the secrets and check NTP. |
| Callback `409 Replayed request` | n8n execution | Request IDs are single-use. Retry the node: it generates a new ID. |
| Send stuck in `sending` (crash between claim and record) | *Recent sends* | **Never just requeue.** First check Gmail → *Sent*. If the message is there, record it with SQL: `select outreach_record_send('<send_id>', 'sent', '<gmail message id>', null);`. If not: `select outreach_record_send('<send_id>', 'failed', null, 'manual: not sent');`. Then press Send again if you still want it to go out. |
| Send `cancelled` | *Recent sends*, with the reason | Sending switch off, draft changed after approval, contact no longer eligible, or daily limit reached. Fix the cause and press Send again. |
| Too many emails | n/a | Set `OUTREACH_SENDING_ENABLED=false` in Vercel (takes effect on the next request), and/or disable the Gmail node. Queued sends are then cancelled, never sent. |
| Pause all automation | n/a | Deactivate *Ops · Outbox pump*. Events stay in the outbox, and the pump delivers everything due when you reactivate it. |
